# 日志分级与文案规范

## 1. 总体约定

**普通运行过程默认使用 `debug`。`info` 用于面向用户的趣味游戏文本，以及非开发者必须了解的关键状态和操作提示。** `warning` 表示值得关注但仍可安全继续的预期偏离；`error` 表示程序已无法在正常状态下处理的失败。

根据事实和影响选择等级，不根据想要的颜色、展示位置或“看起来重要”调整等级。

所有等级的日志文案优先使用中文，包括开发诊断和面向用户的提示。库名、参数名、协议字段、错误码及其他必要技术标识保留原文；第三方异常消息和堆栈保留原始信息，外层用中文说明业务上下文，不为翻译而丢失诊断依据。

| 等级 | 使用条件 | 典型内容 |
| --- | --- | --- |
| `debug` | 开发诊断、普通流程、预定范围内的波动 | 匹配分数、坐标、耗时、分支选择、常规重试、内部状态转换 |
| `info` | 面向用户的游戏化进展文本，或关键且非报错的用户提示 | 出发、完成、暂停、终止快捷键、键鼠控制及释放确认 |
| `warning` | 功能未按预期实现，但存在明确的安全继续或降级路径 | 可选统计保存失败、可选功能不可用并跳过、异常偏离后采用备用方案 |
| `error` | 必要条件不成立、操作失败或其他当前任务无法正常处理的异常 | 分辨率不满足要求、必要资源缺失、关键输入控制失败 |

## 2. `info`：趣味文本与关键提示

- 常规用户进展采用简短的趣味游戏文本，可以使用项目已有的游戏语境，但必须保留清晰的事实。
- 只有用户值得关注的阶段变化才输出，不把每一轮识别、点击和等待包装成游戏播报。
- 终止键、键鼠接管、暂停和恢复等关键提示，优先保证操作说明准确，趣味修饰不能遮住按键、后果与当前状态。
- 按键名称必须读取实际绑定或使用已有来源，禁止文案另写一份可能失真的快捷键。
- 用户主动停止是正常控制行为，通常使用 `info`，不能因为任务未完成就标为错误。

文案例子：

| 场景 | 推荐文案 |
| --- | --- |
| 开始执行 | `开拓开始！即将进入自动探索。` |
| 接管输入前 | `即将接管键鼠；按 %s 可终止任务。` |
| 收到停止请求 | `收到撤退指令，正在停止操作并释放键鼠。` |
| 已确认完成清理 | `本次探索已停止，键鼠已释放。` |
| 目标完成 | `战利品已入袋！本轮目标已完成。` |

禁止只输出“命运的齿轮停止了”之类无法判断实际状态的句子。未完成清理时，不能提前打印“键鼠已释放”。

## 3. `debug`：其余普通过程与诊断

- 正常进入函数、读取配置、识别结果、坐标变化、耗时、轮询、按计划重试等统一使用 `debug`。
- 输出能够定位问题的上下文，如目标、当前状态、尝试次数、实际值与阈值，避免只有“失败了”“到这里了”。
- 预期范围内的暂未识别无需 `warning`；超过约定条件并触发异常降级时才升级。
- 高频循环应按状态变化、采样或汇总记录，不能每帧输出同一信息淹没日志。
- 调试日志中的昂贵计算需要等级检查；参数化格式化只延迟字符串拼接，不会延迟函数参数的计算。

## 4. `warning`：可恢复的异常偏离

`warning` 主要用于辅助检查预期是否成立，相当于可恢复偏离的醒目诊断。必须说清“原本期待什么、实际发生什么、现在如何继续”。

例如：`本轮统计文件保存失败，将跳过统计保存并继续任务。`

- 只有统计保存确实属于可选功能时，上述情况才是 `warning`；必要结果保存失败应按任务契约判为 `error`。
- 同一偏离持续出现时避免重复刷屏；首次发生、恢复或影响变化时再记录。
- 不把普通分支或正常空结果当作警告。
- 警告不是放行机制。若安全条件或必要不变量已被破坏，必须进入失败处理，不能打印警告后继续执行。
- 不以 `warning` 代替必须失败的断言或运行条件校验。

## 5. `error`：主动明确报告无法正常处理的失败

- 发现程序无法正常处理的异常时，应主动报错，说明失败原因、受影响操作及必要的用户行动。
- 主动检测到必要前提不满足，即使尚未抛出语言异常，也属于 `error`。
- “无法继续”以当前任务或操作为边界，不要求整个 GUI 进程退出。应用可以保留界面供用户修正后重新启动。
- **打印 `error` 不会自动中止函数。** 报错后必须明确返回失败、抛出异常或进入失败状态，并执行必要清理。
- 异常堆栈在能够决定失败处置的边界记录一次；用户提示保持易懂，诊断信息保留实际原因。

分辨率示例：如果当前任务必须使用 `1920 × 1080`，检查到其他尺寸时应报告：

> 当前分辨率为 2560 × 1440，本任务要求 1920 × 1080。请调整后重新启动任务。

这是 `error`，并应阻止任务启动。若某任务明确支持自动调整，且调整成功，则调整细节可记 `debug`；不能对同一个已成功处理的事件仍虚报错误。

## 6. 复用现有日志设施

本项目已有 [tool/log.py](../../tool/log.py) 中的 `CUS_LOGGER`、日志处理器和 UI 转发能力。新增业务日志应复用现有入口，不重新建立一套日志封装、处理器或 `print` 通道，也不通过直接调用 UI 输出绕过等级规则。

以下片段仅演示日志调用，变量由业务上下文提供；不表示已实现停止、清理或分辨率处理：

```python
from tool.log import CUS_LOGGER

CUS_LOGGER.debug("目标匹配：score=%.3f, threshold=%.3f", score, threshold)
CUS_LOGGER.info("即将接管键鼠；按 %s 可终止任务。", stop_key)
CUS_LOGGER.warning("本轮统计保存失败，将跳过保存并继续任务：%s", reason)
CUS_LOGGER.error(
    "当前分辨率为 %s × %s，本任务要求 1920 × 1080。请调整后重新启动任务。",
    width,
    height,
)
```

- 普通字符串拼接优先使用日志参数化形式，遵循已有日志接口支持的参数。
- 日志等级与展示策略分别处理，不能为了在 UI 可见而把调试信息改成 `info`。
- 不为一个业务调用新增薄日志包装；确有跨模块统一需求时，在现有设施中集中处理。
- 不输出密钥、凭据和无必要的用户数据；路径、截图和识别文本只记录排障所需部分。
- 不让日志记录改变业务状态，也不依赖某条日志作为其他模块的控制信号。

### 日志文件命名

按分钟命名的日志文件名统一由 `tool/log.py` 的 `timed_log_filename()` 生成，不要在其他模块里自行拼接：

- 正常运行写 `log_年-月-日-时-分.txt`。
- 测试运行由 `test/__init__.py` 设置环境变量 `SIMS_TEST_LOG_PREFIX=test_`，同一入口据此写出 `test_log_年-月-日-时-分.txt`，便于区分测试产物与正常运行产生的日志。
- 测试日志同样纳入 `tool/cleanup.py` 的日志清理规则。

## 7. 等级判定顺序

1. 当前任务已无法正常处理，或必要前提不满足：`error`，进入失败处理。
2. 出现预期之外的功能偏离，但有明确安全的继续路径：`warning`。
3. 属于用户需要知道的游戏进展或关键操作提示：`info`。
4. 其余普通过程和开发诊断：`debug`。

“重试”本身不决定等级：计划内重试为 `debug`，异常降级为 `warning`，最终无法完成必要操作为 `error`。
