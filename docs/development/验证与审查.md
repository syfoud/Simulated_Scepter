# 开发流程、验证与审查

## 1. 修改前建立依据

1. 明确预期结果和不应改变的行为，阅读相关代码、调用方和项目说明。
2. 检查工作区已有改动，避免覆盖或混入他人的工作。
3. 搜索能够复用的实现、字段、状态和日志入口。拟新增内容应能说明为何已有语义不足。
4. 缺陷修复尽量先复现；无法复现时说明证据和不确定性，不能把推测写成已确认原因。
5. 明确验证入口，区分纯计算测试、外部资源测试和会实际操作键鼠的实机测试。
6. 按[运行环境规范](运行环境与命令执行.md)确认项目目录、uv 路径和解释器。依赖以 `pyproject.toml` 为准，Python 命令通过 uv 执行。

## 2. 实现过程中保持完整

- 修改业务规则时同步检查所有相关调用点，避免旧分支继续使用旧规则。
- 移除旧实现前检查引用、外部契约和数据兼容性；不得保留无人使用的并行实现充当保险。
- 不提交调试残留、无用导入、被注释的大段旧代码和没有实际使用者的辅助函数。
- 不为顺便清理扩展范围，但本次修改造成的失效代码和文档必须一并处理。
- 公共接口或存储格式变化应说明迁移方式，不能静默让已有配置或历史数据失效。

## 3. 按行为和风险验证

| 改动类型 | 必要验证方向 |
| --- | --- |
| 文档与注释 | 链接、术语、示例一致性及与实现是否相符 |
| 纯计算或规则 | 典型输入、关键边界、原有行为与失败结果 |
| 复用或重构 | 原调用方与新调用方行为一致，必要副作用不变 |
| 状态转换 | 合法转移、非法转移、暂停、停止、失败及清理 |
| 日志调整 | 等级、用户文案、真实状态、异常堆栈及重复输出 |
| 键鼠与 UI | 前置条件、接管与释放、停止响应；按实际环境补充实机确认 |

- 测试验证外部行为和关键不变量，不机械复述实现，不以私有函数调用次数代替业务正确性。
- 缺陷修复优先补充能暴露原缺陷的回归验证。低风险文档修改无需为了流程新增程序测试。
- 使用项目已配置的工具和相关测试，不假定所有 `test/` 脚本都可无副作用地自动执行；`test/__init__.py` 的 `MANUAL_TESTS` 登记不参与自动发现的手动调试脚本，需要时按原方式单独运行。
- 先运行与改动直接相关的检查，必要时扩大范围；没有新改动或未解决风险时不反复运行同一检查。
- 禁止删除有效测试、弱化断言、硬编码测试结果或绕过检查以取得“通过”。
- 无法进行实机或人工验证时明确标为未完成，不把静态阅读、模拟输入描述为实机通过。

## 4. 合并前检查清单

- [ ] 已检索并优先复用已有实现，没有重新实现相同或相近的业务逻辑。
- [ ] 已检查最终差异，每处改动都直接服务于当前目标或必要的关联修复，没有夹带无关整理，也没有为减少改动而遗留问题根因。
- [ ] 新增变量、字段、参数、配置和抽象各有实际用途，没有固定值伪装的可变配置。
- [ ] 没有同义别名、镜像状态或无理由重复保存的派生值；必要快照和缓存已说明。
- [ ] 自有命名优先采用 1～3 个单词，未滥用前导下划线，必要注释没有被长名称取代。
- [ ] 注释默认中文，docstring 使用 Google 风格，没有复述赋值、循环、返回等语法的无信息量注释，也没有批量格式化无关文档字符串。
- [ ] 单次使用的固定值直接写在使用处并按需解释原因，没有为了命名创建虚假变量或一次性常量。
- [ ] 命名常量具有真实共享语义，各调用处应随同一规则变化，没有仅因数值相同或用途笼统相近而合并。
- [ ] 互斥属性使用单一状态及明确转移，没有靠多个布尔值维持互斥关系。
- [ ] 简单局部状态流采用整数变量和取值说明，没有为状态机强行增加类、枚举或管理器。
- [ ] 没有无职责的多层转发、过度嵌套或为压缩行数制造的复杂表达式。
- [ ] 已沿实际调用检查中间层，没有无意义的函数内嵌套、闭包或仅转手参数与结果的包装。
- [ ] 连续逻辑没有机械拆散，没有为统一外观引入分发框架、反复转换数据或添加无依据的兜底。
- [ ] 新实现已处理其取代的旧逻辑；新增概念确有必要，不能通过直接调整已有流程消除。
- [ ] UI、业务与外部资源的职责清晰，没有循环依赖和跨层重复规则。
- [ ] 异常有明确处置，必要前提失败时不会继续执行，所有出口覆盖资源清理。
- [ ] 普通过程为 `debug`；`info` 文案符合游戏语境且关键操作清晰；警告和错误与实际影响一致。
- [ ] 各等级日志优先采用中文，必要技术标识及原始异常信息保持准确。
- [ ] 日志未提前宣称成功、停止或资源释放，未重复记录同一错误或输出敏感数据。
- [ ] 已完成适当验证，保留了真实结果，并说明未验证项。
- [ ] Python 通过 uv 执行，依赖仍由 `pyproject.toml` 统一声明，没有新增 requirements 文件或隐式升级环境。
- [ ] 未覆盖用户已有改动，相关文档、示例和调用方已同步。
- [ ] 若涉及提交或 PR，每个提交均为完整的原子变更，没有混入独立问题或拆散必须一起生效的修改。

不适用项无需虚构工作；存在例外时记录具体原因，不使用笼统的“历史原因”或“未来扩展”代替解释。

## 5. 交付说明

交付内容应足够让未参与开发的人理解与复核：

- **结果：** 解决了什么问题，用户可观察到什么变化。
- **实现：** 复用了哪部分能力，必要的新设计为何存在。
- **验证：** 实际执行了什么检查，结果如何。
- **限制：** 未验证内容、已知影响及后续所需条件。

不夸大完成程度，不以“应该可以”代替结果，不隐瞒失败的检查。发现无关历史问题时单独说明，不混入本次任务扩大修改范围。

需要提交或创建 PR 时，继续遵循[提交与 PR 规范](提交与PR规范.md)，使描述与最终差异及实际验证一致。
