# PR 提示词

配合[提交与 PR 规范](提交与PR规范.md)使用。写 PR 时把下面的提示词作为任务开头，
不需要再让模型通读全部规范。

```text
写 PR 前先读 docs/development/提交与PR规范.md，然后只输出三块，不写寒暄和过程。

1. 标题：<类型>(<范围>): <一句话结果>；≤ 30 字；不写“优化/修改一些内容”。
2. 正文：只保留四节，没有内容的节整节删掉：
   - 问题与结果：触发条件、原行为、修改后行为各 1–2 句；判断依据用关键实测数据支撑。
   - 实现与影响：只回答“为什么这样改”和“行为/接口/数据有什么变化”，按模块 3–6 条，不复述 diff。
   - 验证：只写真实执行过的命令与结果；未做的实机/CI 明写“未执行”，不得写成通过。
   - 未完成项：只列真实阻碍。
3. 提交：一个原子提交，消息 = 标题 + 必要正文；无关清理另开 PR。

禁止：贴日志/堆栈、逐文件复述、罗列全部测试类名（给数量 + 代表性命令即可）、
“以后可能用到”式扩展、虚构 Issue 编号、把未验证说成已验证。
信息不足（未验证项、关联 Issue 编号、是否要改行为）时，先问一句再写。
```

## 使用要点

- PR 标题与提交标题保持一致，提交与 PR 可以互相回溯。
- “验证”只写实际执行过的内容；命令应可复跑，未做的检查放到“未完成项”并说明原因。
- 正文以评审能在几分钟内读完为上限，实现细节交给 diff 和代码注释。
