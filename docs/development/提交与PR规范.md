# 提交与 PR 规范

## 1. 范围与分支

- 一个 PR 围绕一个明确问题组织，包含解决问题所需的关联修改；无关重构、格式化、依赖升级分开处理。
- 开始前查看工作区与当前分支，不自动切换分支或拉取上游导致用户工作被混入或覆盖。
- 创建分支时使用简短明确的名称，例如 `fix/input-release`、`docs/dev-rules`，遵循项目已有约定。
- 对大改的提前沟通要求遵循根目录贡献指南；用户已明确授权的工作不重复索要同一授权。

## 2. 提交内容

- 提交前检查差异与暂存区，只暂存本次任务相关文件；混有用户改动时，按具体文件或变更片段处理，禁止无检查执行 `git add .`。
- 不提交日志、截图、缓存、临时报告、凭据和构建产物，除非它们明确属于本次交付。
- **PR 中的提交必须遵循原子化原则：一个提交只完成一个完整、可审查的逻辑变更。** 相关实现、必要测试和配套文档一起提交，不能把必须一起生效的改动拆成不可用的中间版本。
- 不按文件数量或操作时间机械拆分提交，也不把独立问题塞进同一提交。每个提交应保持项目可用，并能清楚说明目的、验证范围和回退影响。
- 一个 PR 可以包含多个按依赖顺序组织的原子提交，但应共同服务于该 PR 的目标；可独立交付的无关目标另开 PR。整理提交历史仍需遵守下文的授权边界。
- 提交信息采用 `<类型>(<范围>): <结果>`，范围可省略。例如 `fix(input): 修复停止后按键未释放`、`docs: 补充运行环境与日志规范`。
- 类型应与实际变化一致：行为修复用 `fix`，新行为用 `feat`，保持行为的结构调整用 `refactor`，文档用 `docs`。不能用“重构”掩盖功能变化。

## 3. PR 标题与正文

- 标题直接说明问题或最终结果，避免“优化代码”“一些修改”等空泛描述。
- 正文开头说明具体触发条件、原行为和修改后的行为，使未参与讨论的审查者能够理解。
- 解释关键实现选择、复用关系、兼容性或数据迁移影响，不按文件逐项复述差异。
- 验证必须写实际命令与结果；未执行的实机、人工或 CI 检查明确标注，不能勾选为通过。
- 简单修改用一两段加验证说明即可；复杂修改或仓库模板有要求时再分节。
- 任务范围变化后，重写标题和正文以反映最终实现，不保留过时计划、聊天经过或已放弃方案，除非其原因影响审查判断。
- 关联真实存在的 Issue；只有确实解决其全部要求时才使用自动关闭语法，不能虚构编号。

正文按下面四节组织，没有内容的节整节删除：

```markdown
## 问题与结果
## 实现与影响
## 验证
## 未完成项
```

不用日志片段、逐文件差异复述和全部测试类名占满正文；验证只写实际执行过的命令与结果，
未执行的检查放进“未完成项”说明原因。需要时可直接复制[PR 提示词](PR提示词.md)交给 AI 生成正文。

## 4. 发布与审查

- 本地修改、提交、推送、创建 PR 和合并是不同动作，按用户授权范围执行；只要求编辑文档不代表要求发布 PR。
- 已明确要求创建 PR 时，完成内容和验证后继续执行，不为已授权步骤重复询问。
- 仍有必要验证或问题未解决时，明确状态，必要时使用草稿 PR；不伪装成可合并状态。
- 创建 PR 前检查目标仓库、目标分支和最终差异，确保没有混入其他任务的提交。
- 使用工具提交多行正文时保留真实换行；CLI 优先通过正文文件传递，避免 Shell 转义改变内容。
- 响应审查意见时给出具体修改或技术依据；修改后运行受影响的验证，并更新 PR 描述中的结果。
- 不为绿灯而移除检查或弱化测试。没有通过的检查必须说明；未获得结果的 CI 不能声称通过。
- 不擅自合并、强制推送、删除远端分支或改写他人提交历史。已有明确授权时仍应核对目标和影响。

发布前使用[验证与审查清单](验证与审查.md)逐项核对适用内容。
